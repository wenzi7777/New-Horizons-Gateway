# @nhgw/node

**NH Studio (headless)** -- `nh-studio`, for machines without a screen (the
lab hosts that ran the Python Gateway). It relays like the Studio app and the
Desktop lists it under NH Studio / NH Pocket (`client_type: "studio"`).

- Dropped into the old Gateway folder (or started beside it) it takes the
  Python Gateway's config over, `gateway_id` included, so the server sees the
  same relay (`src/legacyImport.ts`).
- App token (made on the server's Relays page): `nh-studio --set-token`
  reads it from stdin (`--clear-token`, `--token-status`), or the web UI's
  Connection page from this machine (127.0.0.1 only). It is stored with the
  server it was entered for and sent only there; `/api/status` shows it
  masked.
- Web UI on port 5052, terminal UI on a TTY, `--plain` for log lines.

The desktop host for the Gateway core: Node UDP/WebSocket/HTTP/files, the web
UI, the terminal UI (`src/tui/`), self-update (`src/installer.ts`) and the
single-executable build (`scripts/build-sea.mjs`).

## Building the executables

The Gateway ships as one Node SEA (single executable application) per
platform: `darwin-arm64`, `darwin-x64`, `win32-x64`, `linux-x64`,
`linux-arm64`. On any of them, from `ts/`:

```bash
npm ci
npm run build:sea            # -> dist/<platform>-<arch>/nh-gateway[.exe]
npm run build:sea -- --json  # same, result as JSON (output, platformKey, sha256, size)
npm run build:sea -- --dry-run --json   # the plan only
```

Steps: esbuild bundles `src/cli.ts` into one CommonJS file (node22; a SEA's
main script can only `require()` built-ins), `node --experimental-sea-config`
turns it into a blob together with the web UI (`webui/*`, plus
`ui-tokens/src/tokens.css` as `tokens.css`; read them with
`require('node:sea').getAsset(name)`), the running `node` binary is copied,
`postject` injects the blob, and on macOS the signature is removed before and
an ad-hoc signature (`codesign --sign -`) added after. The printed `sha256`
and `size` go into the release manifest (`gateway-bin-*.json`, per platform
key, with the asset `url`).

The node binary must be Node 22 and the *same* binary that generates the
blob (`--node` sets both), since a blob only loads into the Node version that
made it.

### GitHub Actions

Build each target natively, one matrix job per runner (no workflow file is
checked in yet):

| platform key   | runner              | notes |
|----------------|---------------------|-------|
| `darwin-arm64` | `macos-14`          | |
| `darwin-x64`   | `macos-13`          | `macos-13` is being retired by GitHub; use `macos-15-intel`, or build on `macos-14` with `--node <node-v22.x-darwin-x64>/bin/node --platform-key darwin-x64` (runs the x64 node under Rosetta to make the blob; `codesign` signs either architecture) |
| `win32-x64`    | `windows-latest`    | output `nh-gateway.exe`; no signing step (see below) |
| `linux-x64`    | `ubuntu-latest`     | |
| `linux-arm64`  | `ubuntu-24.04-arm`  | |

Per job: `actions/setup-node` with `node-version: 22.x` (pin the exact
version so all five match), `npm ci` in `ts/`, `npm run build:sea -- --json >
build.json`, upload `dist/<key>/nh-gateway*` and `build.json` as artifacts. A
final job collects the five `build.json` files into `gateway-bin-*.json`
(url/sha256/size per key) and attaches the binaries to the release.

Cross-building without the target runner works for Linux and Windows too
(download that platform's official Node 22 binary and pass `--node`/
`--platform-key`), but the blob is generated by running `--node`, so it needs
an emulator (qemu/Rosetta) or the same-version host node; the native matrix
is simpler.

### Signing caveats

- **macOS**: the ad-hoc signature is enough to run on Apple Silicon from a
  terminal and for self-update (the Gateway downloads with `fetch`, which sets
  no quarantine attribute). A copy downloaded with a browser is quarantined
  and Gatekeeper refuses an ad-hoc signed binary: `xattr -d
  com.apple.quarantine nh-gateway`, or sign with a Developer ID and notarize
  (`codesign --sign "Developer ID Application: …" --options runtime
  --entitlements …` needs `com.apple.security.cs.allow-jit` and
  `allow-unsigned-executable-memory` for V8).
- **Windows**: unsigned, so SmartScreen warns on a browser download ("More
  info → Run anyway"). Authenticode-signing (`signtool sign`) must happen
  after `postject`; the copied `node.exe` signature is invalid after
  injection, which is harmless when unsigned.
